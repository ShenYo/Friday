## v1.6.0 (2026-11-27)

Friday v1.6.0 is a MINOR release: the guard and the Git hooks changed, and there is a new seed.
**A consumer must act**: v1.6.0 changes managed-core files (the new `.agents/bin/check-auto-merge`,
`guard-collaborative-git.sh`, `guard-protected-paths.sh`, `check-collaborative-git.sh`, `agent-rules.md`,
the two Git rules documents and the `create-pr` Skill), so `friday-propagate` opens a sync pull request
in each consumer; merge it. The new `.agents/auto-merge` seed is not carried by propagation: copy it by
hand as Seed changes below says.

- **Consumers inherit the auto-merge rule, gated by a check**
  ([#96](https://github.com/ShenYo/Friday/issues/96)). An agent may now arm auto-merge, where it was a
  person's checkpoint, only after a fresh-agent review ends with no must-fix or should-fix open and only
  when the new managed script `.agents/bin/check-auto-merge <n> -R <owner>/<repo>` exits 0. It fails closed,
  naming the condition: the opt-out file `.agents/auto-merge`, read from the base branch of the target
  repository (so a change takes effect once merged), is absent or `on`; the repository is owned by a user,
  not an organization; the base branch has exactly one `pull_request` rule with at least one approving
  review, code-owner review, stale-approval dismissal on push and last-push approval, in an `active` ruleset
  with `current_user_can_bypass` `never`; `.github/CODEOWNERS` is, apart from comments, a single `*
  @<owner>` rule; the acting login's `role_name` is `write` with no `GH_TOKEN` or `GITHUB_TOKEN` set (names
  only, a value is never printed); the repository allows auto-merge and the pull request is open. Any API
  error, a 403 included, is a failure, so a free-plan private repository never qualifies. The shared guard
  allows `gh pr merge` with `--auto` only as the whole command `gh pr merge <n> --auto --squash -R
  <owner>/<repo>` and only when the check passes, blocking any other form with the check's reason, including
  `\gh`, quoted and path spellings of `gh`; a `gh api` call naming `enablePullRequestAutoMerge`,
  `mergePullRequest` or a `pulls/<n>/merge` path is refused in its plain spellings ([what still
  passes](../../payload/.agents/docs/git-guideline/safety-boundary.md#what-neither-layer-enforces); the
  server-side ruleset is the control that holds); `--disable-auto` is allowed; a `gh pr merge` without
  `--auto` is blocked as before. `safety-boundary.md` gains "Arming auto-merge", and `agent-rules.md`,
  `git-commit.md` and the `create-pr` skill follow it; `docs/safety.md` and `ADOPTING.md` (both languages)
  say how to qualify and how to opt out. This repository's `AGENTS.md` exception from #94 is now a pointer
  to the shipped rule. New: `tests/check-auto-merge.sh` (gh stubbed, one failing case per condition, one
  mutant per condition) and `tests/auto-merge-hook.sh`. Managed files changed, so propagation carries the
  script and the rules; the seed `.agents/auto-merge` it does not.

- **The protected-paths hook no longer stalls on one long clause**
  ([#97](https://github.com/ShenYo/Friday/issues/97)). On macOS `/usr/bin/awk`, `guard-protected-paths.sh`
  built each token a character at a time and re-walked each one in `glue()`, both quadratic for a long
  token: a quoted clause of 1 MB joined to a later line by a continuation took 76 s, and a 2 MB word of
  escapes ending in a backslash took 22 s; the first is past the 30 s hook timeout. The tokenizer now
  records where a token starts and takes it in one step, `glue()` returns early for a token with no `<` or
  `>`, and the comment test skips a line with no `#`. Both take about 2 s now; which commands are refused or
  allowed does not change. A continued line that holds a `#` and about a million escapes still takes about
  20 s ([safety.md](../safety.md)). Two timing probes (1 MB of 500,000 words; a 3 MB word of escapes) are
  added to `tests/install-smoke.sh` and to `check-collaborative-git.sh`, and each fails with its fix
  reverted. This corrects the 500 KB limit that v1.5.0 and `docs/safety.md` stated. Managed files changed,
  so propagation carries them; no seed change.


### Seed changes

- **Capability:** a file, `.agents/auto-merge`, seeded with the single line `on`, that lets a repository opt out of agents arming auto-merge: `off` disables it, absent or `on` on the base branch of the target repository leaves it to `.agents/bin/check-auto-merge`; a change takes effect only once merged, and anything else fails closed.
- **Who is affected:** a consumer installed before this release has no such file, which counts as `on`; a full install creates it, while `--managed-only` leaves it to be copied by hand. It matters only to a consumer that wants to opt out, since the check itself never passes where the rules cannot be read (a free-plan private repository).
- **Action:** a consumer that does not want agents to arm auto-merge copies `payload/.agents/auto-merge` from the release into `.agents/auto-merge` in a reviewed commit and changes the line to `off`. A consumer that wants to qualify applies the ruleset in [ADOPTING](../../ADOPTING.md#the-server-side-ruleset), gives `.github/CODEOWNERS` the single line `* @your-login` and allows auto-merge in the repository settings.
- **Check:** `.agents/bin/check-auto-merge <n> -R <owner>/<repo>` for an open pull request prints `ok` and exits 0 where the consumer qualifies, and otherwise exits non-zero naming the condition, `opt-out` after the file says `off`.

## v1.5.0 (2026-11-25)

Friday v1.5.0 is a MINOR release: the guard scripts changed. **A consumer must act**: v1.5.0 changes
managed-core files (`guard-protected-paths.sh`, `guard-collaborative-git.sh`, `check-collaborative-git.sh`
and `safety-boundary.md`), so `friday-propagate` opens a sync pull request in each consumer; merge it.
The new ruleset seed is not carried by propagation: copy it by hand as Seed changes below says.

- **The protected-paths guard joins line continuations** ([#93](https://github.com/ShenYo/Friday/issues/93)).
  A backslash-newline splits one Bash command over two lines, so `cp a \` then `../CLAUDE.md` wrote a
  protected file without the scan seeing the target. The guard now checks the command as written and
  again on up to two joined copies of the whole command, which approximate how the shell joins lines: one
  joins every continued line (ignoring quotes, so it only adds refusals), the other does not join a line
  in which a `#` outside quotes and escapes starts a word, as a comment does, so a comment does not hide
  a later continued line (heredoc bodies and `$'…'` quoting are not modelled; only a space or tab before `#` starts a comment, and an escaped quote does not end a double-quoted span). A single clause of about 500 KB or more can exceed the 30 s hook timeout on macOS awk, on v1.4.0 too, and the guard blocks on an awk that cannot split a string into characters. The `cd` chain of each copy is resolved on its own, so a `cd` split across a
  continuation (`c\` / `d a`) is followed in order. The `cd` limit is unchanged: ten distinct relative
  destinations are allowed and eleven refused; a continuation that changes which `cd`s a copy sees can lower it, and it fails closed.
  `guard-protected-paths.sh` and `check-collaborative-git.sh` are managed files, so propagation carries
  them; no seed changed.

- **A release status table** ([#72](https://github.com/ShenYo/Friday/issues/72)).
  `bin/friday-propagate --status <consumer>...` prints one row per consumer: the release tag (checked
  on `origin` as the same annotated tag object, by the checks a run already makes), the `friday-lock`
  state, and the open sync pull request (a head branch starting with `chore/sync-managed-core`) with
  its URL. It is read-only: it never branches, commits, pushes or opens a pull request, and works on a
  dirty tree or a feature branch. It runs a `git fetch` of `origin/main` in each consumer (the only write; it updates
  `origin/main` and `FETCH_HEAD`) and judges the lock on what `origin/main` holds, so a consumer on a feature branch is
  marked `on <branch>, not main` and still shows its state. A missing path, a consumer with no lock on
  `origin/main`, or a failed `gh` is a row with the reason, not an abort. Exit status: 0 all in sync, 3
  something is not in sync, 2 a tool error or an unreadable row. New: `tests/friday-status.sh`. No
  managed file changed, so propagation carries nothing.
- **CI checks that each paired document agrees in both languages**
  ([#77](https://github.com/ShenYo/Friday/issues/77)). New `bin/check-readme-parity.py` compares
  `README.md` with `README.zh-TW.md` and `ADOPTING.md` with `ADOPTING.zh-TW.md`: the `##`, `###` and
  fenced-block counts, the set of numbers (an ordinal such as "the 15th" and a sentence-final number
  count; list and heading markers do not), the paths of the relative links (which must resolve; anchors
  are not compared) and the terms in the new `bin/readme-stale-terms.txt`, which must be in neither file.
  The `tests` job runs it once per pair; `tests/readme-parity.sh` proves it fails on a dropped section, a
  changed number, a dead link and a stale term, and that a mutant with any one check disabled is caught.
  Friday's own tooling: no managed file changed, so propagation carries nothing.
- **A ruleset a consumer can apply** ([#74](https://github.com/ShenYo/Friday/issues/74)).
  The new seed `payload/.github/rulesets/main.json` is a GitHub ruleset for the default
  branch, in the shape the REST API accepts: `deletion`, `non_fast_forward`, and a
  `pull_request` rule with one approving review, code-owner review, stale approvals dismissed on
  push, last-push approval and resolved threads, with the repository admin role as a
  `pull_request`-mode bypass actor, on the default branch only (`~DEFAULT_BRANCH`). It has no
  required status checks, which differ per repository. The managed `safety-boundary.md` gains a
  section with the command that applies it (`gh api`, by the repository's admin), the command that
  reads it back and compares, the status-check rule to add, and two limits: a private repository on
  a free GitHub plan cannot use rulesets, and an agent that works through an admin login is not
  bound by the ruleset. The ruleset does not make the merge a person's; that rule stays
  instruction-only.
  `docs/safety.md` and `ADOPTING.md` (both languages) state the free-plan limit. The install and `friday-lock`
  still never call GitHub. New: `tests/ruleset.sh`. A managed file changed, so propagation carries
  the doc; the seed it does not.

- **The protected-paths guard closes the ordinary spellings left out of #61**
  ([#73](https://github.com/ShenYo/Friday/issues/73)). Each was probed against the guard at v1.4.0;
  these were allowed and are now refused: `X=1 cd dir && ...` (an environment prefix on `cd` or `pushd`,
  which was not followed), a `cd` inside backticks (`` a=`cd dir && echo x > f` ``; a backtick `cd` with an
  unreadable destination is skipped, as for `$(...)`), the clobber redirection `>|`, `cp`/`mv`/`install`
  with `-t DIR` or `--target-directory=DIR` (DIR and DIR/each source are judged), `ln -sf` (the link target
  and the link name), `sed -i.bak`, `--in-place=.bak` (the backup file is judged too) and `sed -E -i` (`-i` may now follow flags that take no argument),
  and `tee FILE > /dev/null` (a redirection is dropped before the operands are read, so `cp a FILE 2>/dev/null`
  is judged too; `tee` judges every operand; `-tDIR`, bundled `-vtDIR` (not `-oroot`), `--`, and quoted or partly quoted operands (with spaces, glued to a redirection) are read, and a `ln -t` source is judged; an environment prefix, `builtin` or `command` before a backtick `cd` is followed). A command was already refused when its `cd` destination was
  in backticks (`` cd `echo ..` ``): that one is dropped from the list. The long-command stall was
  `${command//[[:space:]]/}` on bash 3.2 (macOS), super-quadratic in the command's length (300 redirections
  took about 16 s, 1,500 minutes), plus a quadratic de-duplication of judged paths; both are now near-linear
  (paths are de-duplicated with one `sort`, which is refused if it fails; a 130,000-character command takes about 2.5 s). The probes are cases in `check-collaborative-git.sh` and
  `tests/install-smoke.sh`, each beside a near-miss that must stay allowed. `guard-protected-paths.sh` is a
  managed file, so propagation carries it; no seed changed. `guard-collaborative-git.sh` had the same
  `${command//[[:space:]]/}` blank check and takes the same regex test.

### Seed changes

- **Capability:** a file, `.github/rulesets/main.json`, that gives the default branch the server-side protection the safety boundary assumes: no deletion, no force push, changes through a pull request with the code owner's approval.
- **Who is affected:** a consumer installed before this release has no such file; a full install gets it, while `--managed-only` leaves it to be copied by hand. It matters only where rulesets are available (a public repository, or a private one on a paid plan).
- **Action:** copy `payload/.github/rulesets/main.json` from the release into the consumer in a reviewed commit, add a `.github/CODEOWNERS` line `* @your-login` and the required status checks, then have the repository's admin apply it with the commands in `.agents/docs/git-guideline/safety-boundary.md` (the section "The server-side ruleset"). Applying is the owner's step, never an agent's.
- **Check:** the read-back `diff` in that section prints nothing, and `gh api "repos/OWNER/REPO/rules/branches/$(gh api repos/OWNER/REPO --jq .default_branch)" --jq '.[].type'` lists `deletion`, `non_fast_forward` and `pull_request`.

## v1.4.0 (2026-11-22)

- **A consumer can learn on its own that it is behind** ([#7](https://github.com/ShenYo/Friday/issues/7), step 1).
  The new seed `payload/.github/workflows/friday-behind.yml` runs weekly and on `workflow_dispatch` in
  the consumer's own repository, takes the highest release tag of Friday from `git ls-remote --tags`,
  checks Friday out at it and runs the new `bin/friday-behind-notice`, which runs `friday-lock check`
  against that tag. `in sync` opens nothing; any other state (exit 1) opens one issue titled
  `Friday: managed core is not in sync with the latest release`, or edits the open issue with that
  title instead of opening a second one (the lookup reads the newest 1,000 open issues, so an older
  notice in a repository with more open issues than that is missed:
  [#88](https://github.com/ShenYo/Friday/issues/88)); a tool error (exit 2) or a `gh` failure fails the job and opens
  nothing. Permissions are `contents: read` and `issues: write`, with no secret. It is a `!` seed in
  `bin/managed-core.txt`, so the lock never compares it and a consumer may change its schedule. It
  reports only; opening propagation pull requests stays step 2. New: `tests/friday-behind-notice.sh`
  (stateful shim `gh`; opens an issue for a stale or drifted lock and none for an in-sync one, fails
  on a tool error or a `gh` failure; checks the workflow's permissions); the script joins the CI
  shellcheck list. An in-sync run says so when the notice issue is still open (read-only, never
  fails the run), both checkouts use `persist-credentials: false`, and a `concurrency` group keeps
  two runs from overlapping.
  `docs/updating-consumers.md` and `ADOPTING.md` (both languages) describe it. No managed file
  changed, so propagation carries nothing.

- **The seed notes and the previous release read only the tags on `origin`** ([#84](https://github.com/ShenYo/Friday/issues/84)).
  `bin/friday-propagate` still looked at every local release tag when it collected the Seed changes
  sections of a range and when it looked for the release before a commit, so a fork that had fetched
  upstream's tags and merged upstream could get upstream's Seed changes text in its pull request,
  or lose the warning that its own release changed seeds without a section. Both now read only the
  local release tags that are on `origin` as the same tag object, so a tag only this checkout has
  is not read, and `friday-propagate` refuses, naming each, when `origin` lists a release tag that
  this checkout holds as a different object, and gives the `git fetch --force` command that
  replaces them with `origin`'s. The listing is
  the one the tool already makes; with `--tag` it replaces the single-tag query, so each path still
  asks `origin` once. `bin/friday-seed-check` has no network and still reads every local release
  tag; its header says so. No managed file or seed changed, so a consumer does nothing.
- **The default release is the highest release tag on `origin`** ([#82](https://github.com/ShenYo/Friday/issues/82)).
  Without `--release` (`install.sh`) or `--tag` (`bin/friday-propagate`), both tools picked the
  highest `vMAJOR.MINOR.PATCH` tag among all local tags, so a fork that had fetched upstream's tags
  picked upstream's higher tag and refused, or installed an upstream release
  that names upstream's producer. They now list `origin` once (`git ls-remote --tags origin`, the
  same listing serves the per-tag check) and take the highest release tag there. If that tag is not
  in the local checkout the tool refuses and says to fetch tags, without falling back to a lower one;
  an `origin` with no release tag, or one that cannot be read, is refused with nothing written. An
  explicit `--release` or `--tag` behaves as before. `ADOPTING.md`, its zh-TW twin and
  `docs/releases.md` say so, and the advice to keep upstream's tags out of a fork is gone; the fork
  steps also say how to merge colliding changelog headings and that the tag message is the entry.
  No managed file or seed changed, so a consumer does nothing.
- **An adopter-facing README and ADOPTING.md** ([#70](https://github.com/ShenYo/Friday/issues/70)).
  `README.md` now opens with who Friday is for, the two paths (consume releases, or fork and cut
  your own), support, prerequisites and what an adopter can rely on, and `ADOPTING.md` opens with
  the path choice; the owner's pending items are worded as known limits, and the kit location is
  stated to be a convention. The fork path is an ordered procedure (own releases
  numbered above the tags it inherited), and the pages say the adopter runs `friday-propagate` with an
  authenticated `gh`. The same in the zh-TW pages. No managed file or seed changed, so a
  consumer does nothing.
- **A seed change carries a migration note** ([#69](https://github.com/ShenYo/Friday/issues/69)).
  A release that changes a consumer-owned seed needs a hand edit in every consumer, and that
  instruction was ad-hoc prose. An entry for such a release now ends with a `### Seed changes`
  section of four fields (capability, who is affected, action, check), documented in
  `CHANGELOG.md`, with v1.2.0 rewritten into it as the worked example. `bin/friday-propagate` puts
  the section of each release in the consumer's range into the pull request body when the range
  changes a seed (decided from Git, over the `!` entries of `bin/managed-core.txt` at either end
  of the range), reading the changelog from `main` so a section added after a release still
  arrives, and says in one line that none changed otherwise. The new `bin/friday-seed-check`, run by CI, fails when a
  release at or after v1.2.0, or the pending entry, changes a seed and lacks the section.
  Propagation still never writes a seed. No managed file or seed changed, so a consumer does
  nothing.
- **A fork's locks are recognised** ([#68](https://github.com/ShenYo/Friday/issues/68)).
  `bin/friday-lock` had the producer slug `ShenYo/Friday` as a literal where it writes a
  consumer lock and where it reads one, so a fork that cut its own releases could not record
  or recognise its own name. The slug now comes from one place: `PRODUCER` near the top of
  the script, default `ShenYo/Friday`, which the `FRIDAY_PRODUCER` environment variable
  overrides for one command. A fork changes that default once. Existing locks stay valid with
  no edit. A lock naming another producer is still refused, now by a message that names both
  producers instead of calling the file "not a Friday record". The hook messages and the links in
  `agent-rules.md` still point at upstream `ShenYo/Friday`: they are managed-core files, and
  `ADOPTING.md` and `docs/architecture.md` now say that this is on purpose. No managed file
  or seed changed, so a consumer does nothing.

### Seed changes

- **Capability:** a weekly workflow that opens or updates one issue in the consumer when its managed core is not in sync with Friday's latest release.
- **Who is affected:** a consumer installed before this release has no `.github/workflows/friday-behind.yml`; a new install gets it. Only a consumer that wants the notice needs it.
- **Action:** copy `payload/.github/workflows/friday-behind.yml` from the release into the consumer in a reviewed commit; a fork changes the `FRIDAY_REPO` line at the top. Issues must be enabled in the consumer.
- **Check:** run the workflow from the consumer's Actions tab (`workflow_dispatch`): on an in-sync consumer it ends green and opens no issue.

## v1.3.0 (2026-11-13)

- **Protected-paths guard follows `cd`** ([#61](https://github.com/ShenYo/Friday/issues/61)).
  The Bash scan judged a relative write target from the hook's working directory only, so
  `cd <consumer> && printf x > AGENTS.md` wrote a listed file with exit 0. A relative target is
  now judged from the working directory and from every literal `cd` or `pushd` destination in the
  command. When the command anywhere contains a destination the scan cannot read (`cd "$X"`,
  `cd -`), or more than about ten distinct relative destinations, nested or in sibling subshells
  (eleven `(cd pkgN && …)` packages), every relative target is
  refused: write it with an absolute path instead. A `cd` that opens a command substitution
  cannot move the shell and is skipped. A redirection or `cp`/`mv`/`tee` target inside a
  subshell no longer carries the `)` into the path, so `(… > AGENTS.md)` and
  `( cp a AGENTS.md )` are judged too. Judging no longer forks per conf line or per directory
  level, so a command that runs ten package builds in subshells, the most the cap allows, is
  judged in about a second.

  **MINOR: a guard script changed.** No seed changed, so a consumer only takes the sync PR that
  `friday-propagate` opens.

## v1.1.0 (2026-10-26)

Friday v1.1.0: consumer setup, and installing from a release

What runs changed, so this is a MINOR release.

- .agents/bin/setup.sh joins the managed core (15 files). Run it after
  cloning a consumer, and again after its Skills change: it sets
  core.hooksPath (per-clone, so a fresh clone otherwise runs no Git
  hooks), checks the runtime guard links, creates AGENTS.md or
  CLAUDE.md only when missing, and links every Skill into
  .claude/skills. It never overwrites what it did not create.
- CLAUDE.md becomes a consumer-owned seed.
- install.sh installs the newest release by default (or --release
  vX.Y.Z), from the release's own tree, so a development checkout
  cannot leak into a new project; --managed-only takes only the
  managed core into an existing project; --working-tree is for
  Friday's own development.
- The self-check no longer leaves two temporary directories behind.

### What a consumer must do

Merge the sync pull request friday-propagate opens; then run
`bash .agents/bin/setup.sh` once in each clone.
