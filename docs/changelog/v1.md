# Friday changelog: v1

The v1 release notes, newest first. How entries are written, and where the other
major versions are, is in [`CHANGELOG.md`](../../CHANGELOG.md).

## Unreleased

- **A fork's locks are recognised** ([#68](https://github.com/ShenYo/Friday/issues/68)).
  `bin/friday-lock` had the producer slug `ShenYo/Friday` as a literal where it writes a
  consumer lock and where it reads one, so a fork that cut its own releases could not record
  or recognise its own name. The slug now comes from one place: `PRODUCER` near the top of
  the script, default `ShenYo/Friday`, which the `FRIDAY_PRODUCER` environment variable
  overrides. A fork changes that default once. Existing locks stay valid with no edit, and a
  lock naming another producer is still refused. The hook messages and the links in
  `agent-rules.md` still point at upstream `ShenYo/Friday`: they are managed-core files, and
  `ADOPTING.md` and `docs/architecture.md` now say that this is on purpose. No managed file
  or seed changed, so a consumer does nothing.

## v1.3.0 (2026-11-13)

- **Protected-paths guard follows `cd`** ([#61](https://github.com/ShenYo/Friday/issues/61)).
  The Bash scan judged a relative write target from the hook's working directory only, so
  `cd <consumer> && printf x > AGENTS.md` wrote a listed file with exit 0. A relative target is
  now judged from the working directory and from every literal `cd` or `pushd` destination in the
  command. When the command anywhere contains a destination the scan cannot read (`cd "$X"`,
  `cd -`), or more than about ten distinct relative destinations, nested or in sibling subshells
  (eleven `(cd pkgN && …)` packages), every relative target is
  refused: write it with an absolute path instead. A `cd` that opens a command substitution
  cannot move the shell and is skipped. A redirection or `cp`/`mv`/`tee` target inside a
  subshell no longer carries the `)` into the path, so `(… > AGENTS.md)` and
  `( cp a AGENTS.md )` are judged too. Judging no longer forks per conf line or per directory
  level, so a command that runs ten package builds in subshells, the most the cap allows, is
  judged in about a second.

  **MINOR: a guard script changed.** No seed changed, so a consumer only takes the sync PR that
  `friday-propagate` opens.

## v1.2.0 (2026-11-11)

- **Protected-paths guard** joins the managed core as
  `.agents/hooks/guard-protected-paths.sh` (the 16th file), with a consumer-owned
  `.agents/protected-paths.conf` seed that has no active entries, a Claude-only link made by
  `setup.sh`, and Claude hooks on `Bash` and on `Write|Edit|MultiEdit|NotebookEdit`. Each target
  is judged by the project that owns it, and the launcher falls back to `CLAUDE_PROJECT_DIR` for
  an unrelated repository, so a session that moves into another repository is no longer blocked
  with `required guard unavailable`. A consumer that already has its own copy reconciles it with
  the shipped one and its conf with the seed. `check-collaborative-git.sh` now checks the link and
  the wiring. It moved here because a consumer carried it alone, unreviewed centrally, and missed
  the launcher fallback: a session whose cwd moved into another repository had every call refused.

  **This is a MINOR change, and an existing consumer must act.** `.claude/settings.json` and
  `.agents/protected-paths.conf` are seeds, which propagation never carries. In the consumer:
  add the two protected-paths launcher hooks (under `Bash` and under
  `Write|Edit|MultiEdit|NotebookEdit`) to `.claude/settings.json`, copied from the payload;
  add `.agents/protected-paths.conf` (the seed, or its own list); and run
  `bash .agents/bin/setup.sh`. Until the hooks and the link are in place,
  `check-collaborative-git.sh` fails, as intended, so the propagate PR's verification fails unless
  that reconciliation is in the same PR. The checker does not require the conf: without one the
  guard protects nothing.
- **`github-pr-verify` joins the managed core** as the 17th file,
  `.agents/skills/git/github-pr-verify/SKILL.md`. It verifies a specified or
  current branch's pull request and updates its Definition of Done evidence. It is generalised so
  it no longer names one consumer's files: it reads the PR template and the routed verification
  rules when present, runs the avoid-list grep only when `.agents/avoid-terms.grep` exists, and
  takes application-code paths from the repository's own rules. Like the other Git Skills it
  runs only when invoked by name, since it edits the pull request body. Two consumers had each kept
  their own hand-copied version of it; now there is one reviewed source.
- **What a consumer must do for `github-pr-verify`.** A consumer that already has its own,
  different copy at that path is not overwritten: `friday-lock check` reports the path as `new in the payload` (so `behind`),
  and `friday-propagate` refuses with "joined the managed core, and this repository has its own
  version" and touches nothing. Reconcile it by hand in a reviewed change: take the release's
  file, move any consumer-specific step the old copy carried into the consumer's own overlay
  documents, then run `friday-lock write`. A consumer with no file there is brought forward by
  propagate as usual.

## v1.1.1 (2026-10-26)

The payload changes only in documentation, so this is a PATCH.

- safety-boundary.md: publishing, editing or uploading to a GitHub Release
  (`gh release create|edit|upload`, or the same through the API) is a
  human-review checkpoint on the same terms as pushing a tag: an agent does it
  only when the user names the release and its tag in the current turn.
- safety-boundary.md: deleting a GitHub Release (`gh release delete`) is
  named among the permanently prohibited operations, beside deleting a
  repository.
- Each release now carries a note people can read: this changelog, the
  annotated tag's message and the GitHub Release share one text, and the
  READMEs and AGENTS.md state the process.
- friday-propagate no longer prints "could not open directory" when a
  managed file joins the core in a directory a consumer lacks.

### What a consumer must do

Merge the sync pull request friday-propagate opens; nothing else.

## v1.1.0 (2026-10-26)

Friday v1.1.0: consumer setup, and installing from a release

What runs changed, so this is a MINOR release.

- .agents/bin/setup.sh joins the managed core (15 files). Run it after
  cloning a consumer, and again after its Skills change: it sets
  core.hooksPath (per-clone, so a fresh clone otherwise runs no Git
  hooks), checks the runtime guard links, creates AGENTS.md or
  CLAUDE.md only when missing, and links every Skill into
  .claude/skills. It never overwrites what it did not create.
- CLAUDE.md becomes a consumer-owned seed.
- install.sh installs the newest release by default (or --release
  vX.Y.Z), from the release's own tree, so a development checkout
  cannot leak into a new project; --managed-only takes only the
  managed core into an existing project; --working-tree is for
  Friday's own development.
- The self-check no longer leaves two temporary directories behind.

### What a consumer must do

Merge the sync pull request friday-propagate opens; then run
`bash .agents/bin/setup.sh` once in each clone.

## v1.0.0 (2026-10-25)

Friday v1.0.0: the first tagged payload release

The managed core as pet_care and Finance hold it today, plus one change:

- safety-boundary.md: pushing a tag is a human-review checkpoint. An
  agent pushes a tag, including through --tags, --follow-tags or
  push.followTags, only when the user names the tag and its commit in

records "tag": "v1.0.0".

From this release on, friday-propagate carries only releases.
